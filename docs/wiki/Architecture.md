# Architecture

Zenith OS uses a monolithic x86_64 kernel with modular supporting crates.

## Layers

| Layer | Location | Responsibility |
|---|---|---|
| Boot | `boot/`, `kernel/src/arch/x86_64/` | Limine handoff, long-mode trampoline, descriptors |
| Kernel | `kernel/src/` | Paging, interrupts, scheduler, compositor/window manager, consoles, hardware probing, syscall setup |
| Filesystems | `filesystem/zenith-fs/` | Zenith FS v5, FAT32, NTFS, ext4, VFS trait |
| Drivers | `drivers/` | Driver framework and device skeletons |
| GUI | `gui/zenith-ui/` | Software `Surface`/theme model; the live desktop is kernel-side |
| Userland | `userland/` | Seven application libraries and host harnesses |
| Tooling | `tools/` | Image and filesystem generators |

## Workspace

All crates are members of the root `Cargo.toml` workspace. The release profile
uses size optimisation and `panic = "abort"`.

The kernel depends on `zenith-fs` for its filesystem drivers and on a global
bump allocator (`kernel/src/allocator.rs`) so `alloc` types are available in
`no_std` kernel code.

## Boot and kernel split

The assembly entry point owns `_start` in the legacy/PVH path and
`limine_start` in the native Limine path. Rust exposes `kernel_main`, which
initialises subsystems in order: consoles, page tables, filesystem support,
interrupts/timer, drivers, scheduler.

## Design properties

- **Independent**: no Linux kernel or existing OS is used; Limine is the only
  external bootloader component.
- **`no_std` libraries**: filesystem, GUI, and application libraries use
  `extern crate alloc` with explicit imports.
- **Modular**: components communicate through small traits (`BlockDevice`,
  `FileSystem`, `Driver`) or plain Rust APIs.
- **Reproducible images**: disk and ISO images are generated by scripts that
  embed test partitions with known contents.
